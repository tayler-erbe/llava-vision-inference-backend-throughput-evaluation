TAYLER ERBE / PERFORMANCE ENGINEERING · VISION MODEL SERVING

The GPU was idle. The server was the bottleneck.

An archival image classifier was on track to take most of a day for one collection, and the GPU looked busy. The telemetry said otherwise: the card was running at about a third of its capacity, and sending more requests did not help. The limit was in how the model was served, not in the hardware.

Short version: with the same base model on the same NVIDIA L4, vLLM delivered 3.6 times the throughput of Ollama at eight requests at once. Against the production setup, which also used a heavier model, the gain was 6.2 times.

00 / THE QUESTION

Is the limit
the card or the code?

The pipeline asks a vision-language model (LLaVA, 7B parameters) to describe each archival image and flag sensitive content, returning six fields as JSON. The target collection held 12,125 images.

THE SYMPTOM

Slow and flat

Sending two, four or eight images at once took no less time per batch than sending one. Throughput did not move.

THE TEMPTATION

Buy a bigger GPU

A slow model on a small card usually reads as a hardware problem. Measured one request at a time, vLLM looked only modestly faster than production.

THE TEST

Measure at real load

Run the same images, prompt and card through two serving stacks at one, two, four and eight requests at once, with telemetry throughout.

FINDING 01

3.6× from serving alone

With the same base model on both servers, vLLM did 55.4 images a minute against Ollama's 15.3. That is the part of the gain that comes from the serving stack.

FINDING 02

6.2× against production

Against the production setup (8.9 images a minute), the gain also includes a lighter model. At that rate the 12,125-image collection drops from about 22 hours to under 4.

FINDING 03

One at a time hid it

At a single request, vLLM was no faster than Ollama on the same model (13.0 against 14.9 a minute). The difference appears only under concurrent load.

How the bottleneck was found.

Throughput alone said "slow". The telemetry said why: on Ollama, requests waited in a queue while the GPU stayed underused.

Signals observed on Ollama and what they indicate
Signal on OllamaWhat was measuredWhat it means
ThroughputFlat from one to eight requestsNo requests processed in parallel
Response time8.2× longer at eight requests than at one (vLLM: 1.9×)Requests queued one behind another
GPU use26 to 31% and 54%, whatever the loadThe card had spare capacity
Power drawAbout 49 W and 60 W of a 72 W capNot at its power limit
GPU memoryConstant at 6,139 MB and 5,191 MBNo extra memory per request in flight

The same signature on two models. Both Ollama configurations behaved the same way, which points to how Ollama 0.3.14 schedules requests for this workload, not to either model. vLLM held the GPU at 96 to 97% at every load level.

02 / METHOD

Three experiments,
one instrument.

The prompt was settled first, so that the serving comparison changed only one thing at a time.

  1. 01 / PROMPT

    Lock the prompt

    1,200 calls compared three separate questions per image against one combined question. The combined prompt was 1.61× faster, kept valid output, and made fewer confident mistakes on images with text.

  2. 02 / OLLAMA

    Two models, four loads

    30 images at one, two, four and eight requests at once, on the production model and on the same base model vLLM would serve.

  3. 03 / vLLM

    Same images, same card

    The identical sweep on vLLM 0.6.6 with continuous batching, which combines in-flight requests into shared passes on the GPU.

  4. 04 / MEASURE

    Telemetry throughout

    Every call's timings and token counts, plus GPU use, memory, power, temperature and CPU every half second, saved so each chart can be rebuilt.

03 / LIMITS

What this does
not show.

This is a speed study. It chooses a serving stack; it does not measure classification accuracy.

  • The two servers ran the model at different precision: 4-bit on Ollama, 16-bit on vLLM. The 3.6× figure compares the same base model, not identical weights.
  • Whether the two setups give the same answers on each image was not measured here. Accuracy needs labelled images and its own evaluation.
  • The serving comparison used 30 images at four load levels. The corpus times are projections from that rate, not timed full runs.
  • The Ollama result is for version 0.3.14 on this workload. Later versions may schedule requests differently.
